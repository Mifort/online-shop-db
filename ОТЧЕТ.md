# Что сделано и как

База интернет-магазина поднята в Docker на PostgreSQL 18.6 и заполнена примером. Схема, связи, индексы, процедуры, запросы, триггеры, представления и функции лежат в одном SQL-скрипте, который можно запустить на любом сервере PostgreSQL 11 и новее.

## Файлы

| Файл | Назначение |
|---|---|
| `docker-compose.yml` | Контейнер PostgreSQL 18 |
| `sql/trofimov_viktor.sql` | Решение задания |
| `sql/demo.sql` | Пример данных и проверки |
| `ОТЧЕТ.md` | Этот файл |

## Как запущен PostgreSQL

Образ `postgres:18`. Контейнер называется `pg18-shop`.

У PostgreSQL 18 каталог данных внутри контейнера — `/var/lib/postgresql/18/docker`. Том поэтому подключён к `/var/lib/postgresql`, а не к старому пути `/var/lib/postgresql/data`. Имя тома — `pg18_data`, данные сохраняются после остановки контейнера.

Параметры базы:

| Параметр | Значение |
|---|---|
| Хост | `localhost` |
| Порт | `5432` |
| База | `shop` |
| Пользователь | `shop` |
| Пароль | `shop` |

Проверка готовности: `pg_isready -U shop -d shop`. Сервер отвечает версией `PostgreSQL 18.6`.

Запуск и остановка из каталога проекта:

```bash
docker compose up -d
docker compose stop
```

Повторно накатить схему и пример:

```bash
docker exec -i pg18-shop psql -U shop -d shop -v ON_ERROR_STOP=1 < sql/trofimov_viktor.sql
docker exec -i pg18-shop psql -U shop -d shop -v ON_ERROR_STOP=1 < sql/demo.sql
```

`trofimov_viktor.sql` при повторном запуске удаляет свои объекты и создаёт их заново. Весь скрипт выполняется в одной транзакции: при ошибке база не остаётся наполовину созданной.

## Таблицы и связи

Шесть таблиц. У каждой `id` имеет тип `SERIAL PRIMARY KEY`, как в задании.

- `categories` — `name VARCHAR(255)`, название уникально и обязательно.
- `products` — `name`, `price DECIMAL(10, 2)`, `category_id`. Цена не может быть отрицательной. `category_id` ссылается на `categories.id`.
- `users` — `name`, `email`. Email уникален. `users_email_normalized` требует адрес без пробелов по краям и в нижнем регистре. `users_email_format` требует вид `имя@домен.зона` и действует на любой `INSERT`, не только на процедуры. Процедуры сами приводят адрес к нижнему регистру и сообщают понятную ошибку, если формат неверный. Ограничение не проверяет, что почтовый ящик существует.
- `orders` — `user_id`, `order_date TIMESTAMP`. Дата по умолчанию равна текущему времени. `user_id` ссылается на `users.id`.
- `order_details` — `order_id`, `product_id`, `quantity`. Количество больше нуля. В одном заказе один и тот же товар встречается один раз. Удаление заказа удаляет его позиции.
- `reviews` — `product_id`, `user_id`, `rating INTEGER` от 1 до 5, `comment TEXT`. Один пользователь оставляет один отзыв на товар.

Внешние ключи держат целостность. Обновление `id` родителя каскадом обновляет ссылки. Удаление категории, товара или пользователя блокируется, если на них ещё ссылаются заказы или отзывы. Удаление заказа каскадом удаляет строки `order_details`.

К обязательным полям добавлены два, они нужны дополнительным пунктам:

- `order_details.price DECIMAL(10, 2)` — цена товара в момент заказа. Сумма заказа из-за этого не меняется, когда в каталоге меняют цену.
- `products.rating NUMERIC(3, 2)` — средний рейтинг. Пока отзывов нет, поле пустое. Допустимый диапазон — от 1 до 5.

## Индексы

В PostgreSQL внешний ключ сам индекс не создаёт, поэтому индексы добавлены отдельно, только по полям, которые участвуют в выборках и соединениях.

| Индекс | Зачем |
|---|---|
| уникальный индекс `users.email` | поиск заказов по email |
| `products(category_id)` | товары одной категории |
| `orders(user_id, order_date)` | заказы пользователя и сумма за период |
| уникальный `(order_id, product_id)` | состав заказа: левый столбец индекса уже ищет позиции по `order_id` |
| `order_details(product_id)` | позиции конкретного товара |
| `reviews(user_id)` | отзывы пользователя |
| частичный `reviews(product_id) WHERE rating > 3` | товары, у которых есть отзыв выше 3 |

Частичный индекс меньше полного индекса по всем отзывам: в него попадают только оценки 4 и 5, а запрос задания ищет именно такие отзывы.

## Хранимые процедуры

Процедуры написаны на PL/pgSQL. Добавление возвращает новый `id` через параметр `INOUT`. Изменение и удаление проверяют, что запись существует, и сообщают об ошибке по-русски.

Товары: `add_product`, `update_product`, `delete_product`.
Пользователи: `add_user`, `update_user`, `delete_user`.
Заказы: `add_order`, `update_order`, `delete_order`.
Отзывы: `add_review`, `update_review`, `delete_review`.

Процедуры проверяют пустое имя, отрицательную цену, оценку вне диапазона 1–5, формат email и наличие связанных записей. Повторный email и повторный отзыв того же пользователя на тот же товар завершаются понятной ошибкой. Удаление товара или пользователя, на которых ещё есть заказы или отзывы, тоже завершается ошибкой: PostgreSQL в этом случае отдаёт `restrict_violation`, и процедура перехватывает его вместе с `foreign_key_violation`.

Пример вызова:

```sql
DO $$
DECLARE
    v_id INTEGER;
BEGIN
    CALL add_product('Ноутбук', 89990.00, 1, v_id);
END $$;
```

## Запросы задания

Оба запроса сохранены в базе как функции на чистом SQL. Текст запроса находится в теле функции.

Все заказы пользователя по email:

```sql
SELECT * FROM get_orders_by_email('anna@shop.test');
```

Функция соединяет `orders` и `users`, фильтрует по email и для каждого заказа считает число позиций и сумму `price * quantity`. Email перед сравнением приводится к нижнему регистру, поэтому индекс по `users.email` используется.

Товары категории, у которых есть отзыв с рейтингом выше 3:

```sql
SELECT * FROM get_products_with_high_rating(1);
```

Условие записано через `EXISTS`: товар попадает в результат, если хотя бы один его отзыв выше 3. Соединение с последующим `DISTINCT` здесь не нужно. Для категории «Электроника» возвращается только «Ноутбук» (отзывы 5 и 4). «Наушники» с отзывом 2 не возвращаются.

## Дополнительные пункты

Триггер `trg_order_details_set_price` стоит на `order_details` и срабатывает до вставки и до смены товара в позиции.

- При добавлении позиции он записывает в неё текущую цену из `products`. Переданная в `INSERT` цена заменяется каталожной.
- При смене `product_id` позиция получает цену нового товара.
- Скидка в уже созданной позиции меняет только `order_details.price`. Каталог остаётся прежним.
- Изменение каталога через `update_product` уже сохранённые позиции заказа не трогает.

Триггер `trg_reviews_refresh_product_rating` стоит на `reviews` и срабатывает после вставки, обновления и удаления. Он вызывает `refresh_product_rating`. Та сначала блокирует строку товара (`SELECT ... FOR UPDATE`), следующим оператором считает `ROUND(AVG(rating), 2)` и только потом записывает результат в `products.rating`. Так параллельный отзыв не затирает среднее снимком, снятым до чужого `COMMIT`. Если отзыв перенесли на другой товар, пересчитываются оба, в порядке возрастания `id`, чтобы две такие операции не встали взаимно. После удаления последнего отзыва поле становится пустым.

Представление `v_orders_with_user_and_product` выводит заказ, дату, имя пользователя, название товара, количество, цену позиции и сумму строки. У заказа с двумя товарами две строки.

Представление `v_user_order_stats` для каждого пользователя выводит число заказов и общую сумму. Пользователи без заказов тоже есть в списке: у них 0 заказов и сумма 0. Число заказов считается как `COUNT(DISTINCT o.id)`, чтобы соединение с позициями не увеличивало счётчик.

`user_orders_total(user_id, начало, конец)` возвращает сумму заказов пользователя за полуоткрытый период: `order_date >= начало` и `order_date < конец`. Соседние периоды не делят общую границу, а последний день не обрезается на долях секунды. Сумма берётся из `order_details.price`, то есть из цены на момент заказа.

`product_avg_rating(product_id)` возвращает средний рейтинг по отзывам. Если отзывов нет, результат пустой. Если товара нет, функция сообщает об ошибке.

## Пример в базе

`sql/demo.sql` заполняет магазин и проверяет числа. Проверки триггеров, отрицательной цены и запрета удаления выполняются во второй транзакции и откатываются, поэтому в базе остаётся исходный пример.

Категории: Электроника, Книги, Одежда.

Пользователи: Анна (`anna@shop.test`), Борис (`boris@shop.test`), Вера (`vera@shop.test`). Адрес Анны передан как `Anna@Shop.Test` и сохранён в нижнем регистре.

Товары: Ноутбук 89990.00, Наушники 4990.00, Роман 790.00, Футболка 1990.00.

Заказы:

- 1 октября 2026, Анна: ноутбук и двое наушников, сумма 99970.00.
- 15 октября 2026, Анна: роман, сумма 790.00.
- 10 октября 2026, Борис: три футболки, сумма 5970.00.

Отзывы: ноутбук 5 и 4 (средний рейтинг 4.50), наушники 2, роман 5. У футболки отзывов нет, `rating` пустой.

Проверенные результаты:

- у Анны два заказа, общая сумма 100760.00;
- с 1 октября включительно до 11 октября не включая у Анны только первый заказ, `user_orders_total` возвращает 99970.00; заказ ровно на правой границе в сумму не входит;
- в электронике с оценкой выше 3 один товар — Ноутбук;
- в одежде таких товаров нет;
- у Веры 0 заказов и сумма 0;
- после смены каталожной цены наушников цена в уже созданном заказе остаётся 4990.00;
- скидка в позиции заказа не меняет каталожную цену; смена товара в позиции подставляет цену нового товара;
- адрес с буквами в верхнем регистре напрямую в `users` не сохраняется;
- изменение отзыва ноутбука с 4 на 2 даёт средний рейтинг 3.50, удаление обоих отзывов очищает `products.rating`;
- товар с отрицательной ценой не сохраняется;
- товар, который есть в заказе, не удаляется.
